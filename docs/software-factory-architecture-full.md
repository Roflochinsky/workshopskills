# Software Factory: полная архитектура Pi / OMP, LAW, skills, тестирование и verification

**Эту архитектуру стоит строить, но не как конвейер из десятка специализированных агентов. Я бы сделал одного ведущего агента с подключаемыми skills, внешним контроллером допуска и независимыми проверяющими.**

Главный недостающий элемент — **контракт между намерением, реализацией и доказательством результата**. Сейчас у тебя хорошо намечены инструменты, но ещё не определено, кто устанавливает критерии готовности, кто разрешает исполнение и какие доказательства позволяют принять работу.

И отдельно: проблему «100 тестов на кнопку» нужно решать **до написания кода**, через контракт тестирования. Последующий reviewer уже должен проверять соблюдение этого контракта, а не впервые выяснять, зачем написан каждый тест.

Ниже — предлагаемая архитектура. Я также подготовил [пакет с архитектурой, шестью skills, шаблонами и вариантами Pi/OMP](sandbox:/mnt/data/software-factory-blueprint.zip). Это исходные процедуры и технические задания, **не установленная фабрика**.

## 1. Как должна выглядеть система целиком

В предыдущем ответе я слишком жёстко разделил аналитика, архитектора и исполнителя на отдельных агентов. После изучения статьи Anthropic я бы изменил это решение.

**Ведущий агент сохраняет контекст бизнес-проблемы, обсуждения, прототипа и реализации.** Отдельные агенты появляются там, где действительно нужны независимость, параллельность или другие полномочия. Это соответствует рекомендации Anthropic не воспроизводить организационную структуру команды внутри агентной системы. ([Claude](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop))

```text
Tern
Диалог · spec/ADR · UI-preview · diff · решения человека
                         │
                  Factory Controller
       состояния · допуски · бюджеты · evidence · восстановление
                         │
                 Ведущий агент Pi / OMP
                         │
       Skills, подключаемые по текущей необходимости
                         │
  Grilling → анализ → UI/design → preflight → реализация
                         │
        ┌────────────────┼─────────────────┐
        │                │                 │
  Code Intelligence   Worktrunk      Preview Environment
  LSP + graph +       отдельные      приложение + fixtures
  semantic search     worktrees      + изолированные данные
        │                │                 │
        └────────────────┼─────────────────┘
                         │
              Независимая проверка
          spec review · runtime · RBAC audit
                         │
               Evidence Gate → PR
                         │
           integration CI → rollout → проверка
```

**Factory Controller — не ещё один LLM-агент.** Это обычный программный компонент, который хранит состояния, проверяет условия переходов и выдаёт полномочия.

Вызов `ImplementSpec()` при такой архитектуре не обязан означать создание нового агента. Это может быть запуск процедуры в текущей сессии. А вот независимый `Review()` должен получать отдельный контекст.

### Чего именно не хватает

| Недостающий компонент | Что он должен обеспечивать |
|---|---|
| Контракт задачи | Связь бизнес-проблемы, spec, ADR, UI, критериев приёмки и разрешённого scope |
| Контракт тестирования | Какие риски проверяем, через какие границы и почему нужны именно эти сценарии |
| Внешний контроллер | Допуск к записи, ограничения инструментов, approvals, бюджеты, остановка и восстановление |
| Управление средами | Изоляция не только файлов, но и БД, очередей, аккаунтов, портов и внешних эффектов |
| Проверяемые доказательства | Результаты запусков, привязанные к конкретным SHA, build и версиям требований |
| Управление skills | Версии, зависимости, уникальные имена, совместимость с harness и отсутствие конкурирующих регламентов |
| Оценка самой фабрики | Проверка, что новая архитектура действительно уменьшает переделки, дефекты и стоимость принятого изменения |

В первом приближении всё это может жить в **одном сервисе с транзакционным хранилищем**. Начинать с набора микросервисов не требуется.

## 2. Что брать у Matt Pocock и poteto

Под poteto я использую **pstack из `cursor/plugins`**. Его процедуры полезны, но Cursor-specific инструменты и пути нельзя считать готовыми интеграциями Pi или OMP. ([GitHub](https://github.com/cursor/plugins/blob/main/pstack/README.md))

Я бы собирал следующий набор:

| Этап | Основа | Как адаптировать |
|---|---|---|
| Обсуждение проблемы | Matt: `grilling`, `grill-with-docs` | Сохранять зависимость вопросов; факты выяснять в проекте, бизнес-решения — у тебя |
| Формализация | Matt: `to-spec` + собственный системный аналитик | Дополнить системным анализом, RBAC, ошибками, данными и проверяемостью |
| UI и неопределённые решения | Matt: `prototype` | Проверять конкретную гипотезу, а не сразу писать production UI |
| Реализация | Matt: `tdd`, при необходимости части `implement-spec` | Один ведущий агент; параллельные исполнители только для независимых частей |
| Проверка реального приложения | poteto: `create-verification-skill`, `maintain-verification-skill` | Создать проектный driver с реальными командами, fixtures и evidence |
| Независимая проверка | Matt: `code-review`; poteto: `interrogate`, `swarm` | Развести проверку spec, корректности и воспроизводимых runtime-дефектов |
| Архитектура и PR | Matt: `improve-codebase-architecture`, `pr` | Ограничить аудит областью изменений; оформление PR отделить от push/merge |
| Улучшение процесса | poteto: `automate-me`, `correct` | Извлекать подтверждённые проблемы из сессий, но не менять LAW автоматически |

Эти назначения следуют из самих skills; ниже я добавляю к ним собственные правила допуска и контроля. ([GitHub](https://raw.githubusercontent.com/mattpocock/skills/main/skills/productivity/grilling/SKILL.md))

### Почему нельзя просто установить оба набора

Есть конкретные расхождения.

Например, текущий `to-spec` у Matt после публикации спецификации самостоятельно выставляет `ready-for-agent`. **В твоей фабрике это должно быть запрещено:** спецификация ещё должна пройти preflight и необходимое согласование. ([GitHub](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/to-spec/SKILL.md))

У Matt и poteto есть собственные процедуры `tdd`. Полноценный `poteto-mode` также содержит правила управления всем процессом. Если подключить всё сразу, у ведущего агента появятся несколько конкурирующих способов решать, когда делегировать, когда спрашивать и когда считать работу завершённой. ([GitHub](https://raw.githubusercontent.com/cursor/plugins/main/pstack/skills/tdd/SKILL.md))

Поэтому предлагаю:

**Upstream skills → зафиксированные версии → адаптация → единый активный набор `factory-*`.**

Адаптация должна менять не только название, но и внутренние ссылки на skills, вызовы инструментов, пути файлов и правила автономности. Оригиналы остаются отдельно, чтобы можно было сравнивать обновления.

## 3. LAW: Requirements & Analysis

### Не «максимум текста», а максимум существенных решений

Исполнителю действительно нужно дать достаточный контекст. Но огромная спецификация с сотней однотипных user stories не гарантирует полноту.

Я бы установил правило:

> **Каждая применимая область анализа должна быть рассмотрена. Каждое неприменимое измерение получает N/A с причиной. Критические неизвестные блокируют реализацию.**

Это позволяет не забывать важное, но не превращать исправление подписи кнопки в многодневное проектирование.

### Skill системного аналитика: три уровня

```text
Общее ядро системного анализа
             +
Профиль конкретного проекта
             +
Контракт конкретного изменения
```

**Общее ядро** задаёт метод: исследовать факты, провести grilling, определить поведение, риски и доказательство результата.

**Профиль проекта** содержит предметную область, роли, архитектурные границы, существующие контракты, команды и правила разработки.

**Контракт изменения** содержит только то, что относится к текущей задаче.

Не нужно создавать отдельный аналитический skill для каждого экрана. Нужен один устойчивый метод с проектными данными.

### Что должен выяснить аналитик

| Область | Что должен понимать исполнитель |
|---|---|
| Проблема и результат | Кто испытывает проблему, в каком процессе, что должно измениться и как это заметить |
| Scope | Что делаем, что не делаем, какие зависимости и ограничения существуют |
| Пользовательские сценарии | Основной путь, альтернативы, ошибки, отмена, повтор и восстановление |
| Предметные правила | Состояния объектов, допустимые переходы, предусловия и инварианты |
| Данные | Источник истины, ownership, ограничения, жизненный цикл, удаление и чувствительные данные |
| API и события | Входы, выходы, ошибки, побочные эффекты, повторные запросы и совместимость |
| Доступ | Роль, действие, принадлежность объекта, tenant и состояние ресурса |
| UI | Состояния loading, empty, error, forbidden, dirty; доступность и поддерживаемые размеры |
| Нефункциональные требования | Подтверждённые требования к нагрузке, задержкам, доступности и наблюдаемости |
| Изменение системы | Миграции, rollout, rollback, старые клиенты и данные |
| Приёмка | Критерии, источники ожидаемого поведения, существующее покрытие и способ проверки |

**Аналитик не должен выдумывать численные SLA, правила доступа или бизнес-политику.** Текущая реализация помогает понять фактическое состояние, но не доказывает, что это состояние правильное.

### Как проводить grilling

Предлагаемый порядок:

```text
Проблема → пользователь и процесс → желаемый результат
         → ограничения → варианты решения → существенные решения
```

Сначала агент исследует то, что можно установить из репозитория. Затем спрашивает тебя о целях, приоритетах и выборе между вариантами.

Именно такой характер вопросов предусмотрен в `grilling`: связанные решения, рекомендации по вариантам и самостоятельное исследование доступных фактов. ([GitHub](https://raw.githubusercontent.com/mattpocock/skills/main/skills/productivity/grilling/SKILL.md))

Не нужно начинать с «какой компонент React использовать?», пока непонятно, зачем пользователю новая функция.

### Где создавать UI

**После определения проблемы, но до окончательной фиксации взаимодействия.**

Например, выяснилось, что пользователю нужно массово менять статус записей. Пока неизвестно, нужен ли отдельный экран, действие над выделенными строками или пошаговый сценарий.

Тогда прототип отвечает на этот конкретный вопрос. После обсуждения в spec попадают принятые решения, состояния и ограничения. Сам прототип не становится автоматически production-кодом.

Matt’s `prototype` как раз предназначен для дешёвого исследования неопределённости, включая варианты UI, а не для немедленной полноценной реализации с тестовой обвязкой. ([GitHub](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/prototype/SKILL.md))

### Как сохранить твои spec и ADR

Я бы разделил ответственность так:

**Spec:** что должно работать и как принимается результат.

**ADR:** почему выбран существенный архитектурный подход, какие альтернативы отклонены.

**Execution plan:** какие символы, файлы, команды и шаги относятся к текущей ревизии.

**Test contract:** какие доказательства нужны и почему.

Не стоит дублировать spec в новом каталоге фабрики. Контроллер должен ссылаться на уже существующий документ и фиксировать его версию.

**Допуск к реализации привязывается к версиям spec, ADR, профиля проекта, test contract и согласованному scope.** Изменение бизнес-правила после допуска требует пересогласования. Обычная правка кода требует обновления проверок, но не повторного обсуждения всей задачи.

Готовый [skill системного аналитика](sandbox:/mnt/data/software-factory-blueprint/skills/factory-system-analyst/SKILL.md) включён в пакет.

## 4. LAW: Architecture & Preflight — codegraph, LSP и поиск переиспользования

Здесь важно разделить три разных источника знания.

### Граф кода

Строится из реального source, AST и данных языковых серверов: определения, ссылки, импорты, наследование, поддерживаемые связи вызовов.

### Поисковый индекс

Содержит код, сигнатуры, комментарии, spec и ADR. Позволяет искать по словам и смыслу.

### Знания из сессий

Содержат наблюдавшиеся проблемы, успешные команды, решения и повторяющиеся потребности в инструментах.

**Из сессий нельзя строить достоверный граф текущего кода.** Агент мог ошибиться, описывать другую ветку или обсуждать ещё не реализованное решение.

Сессии полезны для другого: определить, какие поисковые операции нужны, какие команды действительно работали и на каких реальных запросах оценивать качество поиска.

### Какие инструменты нужны ведущему агенту

Ниже — **предлагаемые интерфейсы для разработки**, а не существующие API Pi/OMP:

```text
find_reuse_candidates(...)
    Найти реализации похожего поведения.

get_symbol_context(...)
    Получить определение, ссылки, связанные тесты и решения.

trace_impact(...)
    Найти потенциально затронутые контракты и вызывающий код.

lookup_project_knowledge(...)
    Найти решение или проверенную команду с происхождением.

index_health(...)
    Проверить актуальность индекса и ограничения покрытия.
```

Для `find_reuse_candidates` недостаточно запроса «найди похожий метод».

Нужен запрос примерно такого содержания:

> Найди существующую операцию изменения ответственного за объект: проверка полномочий, ограничение по tenant, запись audit event, повторный запрос не создаёт повторный побочный эффект.

Поиск должен возвращать кандидатов с объяснением сходства и различий, а не один «лучший» результат без оснований.

Предлагаемый механизм:

```text
Поиск по словам + semantic retrieval
                  ↓
Расширение через связи графа
                  ↓
Ранжирование кандидатов
                  ↓
Проверка реальной реализации и контракта
```

После поиска исполнитель обязан открыть код и сравнить предусловия, ошибки, side effects и authorization. **Семантическое сходство — основание изучить метод, а не основание его использовать.**

### Актуальность между worktrees

Результат должен быть привязан минимум к:

```text
repository identity
commit SHA
worktree diff digest
index/extractor versions
```

Индекс `main` нельзя молча выдавать за индекс ветки, где уже поменялись интерфейсы.

При устаревшем индексе допустим переход на `rg` и LSP. Недопустим вывод «аналогов нет», когда поиск просто не покрывает текущие изменения.

### Задание агенту на создание этого слоя

Я подготовил отдельное [техническое задание на Code Intelligence и анализ сессий](sandbox:/mnt/data/software-factory-blueprint/tasks/code-intelligence.md).

В нём сначала требуется исследовать существующие инструменты, затем собрать реальные поисковые задачи из разрешённых сессий проекта и измерить baseline. Только после этого — добавлять semantic index.

Критерии включают поиск при разных именах, rename/delete, разные worktrees, неподдерживаемые языки, устаревшие команды, отсутствие результата и недоверенные инструкции внутри транскриптов.

**Цель — не построить свой поисковый движок ради архитектуры. Цель — уменьшить повторное написание уже существующего поведения.**

## 5. LAW: Verification & Review — правила против избыточных тестов

Это центральная часть.

**Нужен не лимит «не больше пяти тестов», а требование обосновать каждый новый поведенческий сценарий.**

Сто тестов могут быть оправданы для сложной матрицы доступа. Пять тестов могут быть мусором, если они проверяют только настройки mock.

### 5.1. Test contract до реализации

Для каждого обязательного сценария фиксируется:

| Поле | На какой вопрос отвечает |
|---|---|
| `requirement / invariant / risk` | Какое требование или риск защищаем? |
| `behavior` | Какое наблюдаемое поведение проверяем? |
| `distinct_failure_mode` | Какой отдельный дефект должен обнаружиться? |
| `public_boundary` | Через какой публичный интерфейс проверяем? |
| `oracle_source` | Откуда известно правильное поведение? |
| `existing_coverage` | Нет ли уже эквивалентной проверки? |
| `disposition` | Используем существующую, расширяем её или создаём новую? |
| `cost` | Какова стоимость запуска и сопровождения? |

*Oracle* здесь — независимый источник ожидаемого результата: spec, согласованная policy, известный пример, математическое свойство.

**Копия проверяемого алгоритма внутри expected — не независимый oracle.**

Matt’s `tdd` уже требует согласованных публичных границ, проверки поведения и последовательных вертикальных изменений вместо массового написания тестов на воображаемую реализацию. Это хорошая основа, но контракт полезности тестов и gate я добавляю поверх неё. ([GitHub](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/tdd/SKILL.md))

### 5.2. Выбирать границу, а не тестировать каждый слой

Предлагаемое правило:

> Проверять поведение на наиболее высокой стабильной границе, которая даёт достаточно быстрый, надёжный и понятный сигнал для данного риска.

Это **не означает всё проверять через браузер**.

Сложную чистую функцию удобно проверять unit-тестами. Бизнес-операцию с БД и authorization — интеграционно через публичный сервисный или API-интерфейс. Пользовательскую связку формы, запроса и отображения результата — небольшим числом браузерных сценариев.

Один и тот же факт не нужно доказывать на четырёх слоях, если каждый слой не обнаруживает отдельный класс ошибки.

Проверки пользовательского поведения вместо внутренней структуры также соответствуют рекомендациям Testing Library и Playwright. ([testing-library.com](https://testing-library.com/docs/guiding-principles/))

### 5.3. Что запрещать в правилах написания тестов

Я бы явно запретил следующие практики без отдельного обоснования:

- Проверки приватных методов, порядка внутренних вызовов и устройства state вместо внешнего поведения.
- Mock собственного use case, после которого тест подтверждает только настройку mock.
- Большие snapshots всего DOM и проверки CSS-классов, не связанных с согласованным визуальным требованием.
- Одинаковые сценарии на нескольких слоях без различимого дефекта, который ловит каждый.
- Ожидаемый результат, вычисленный тем же алгоритмом или authorization policy, которую проверяем.

При этом **один сценарий может содержать несколько связанных assertions**. Не нужно дробить «данные сохранились, показано подтверждение, после перезагрузки состояние осталось» на три искусственно независимых теста.

Mock нужен прежде всего на внешних границах. Проверка RBAC с подменённой функцией разрешений почти ничего не доказывает о реальной цепочке доступа. Рекомендации Matt по mocking отдельно предостерегают от подмены собственных внутренних компонентов. ([GitHub](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/tdd/mocking.md))

### 5.4. Пример: кнопка «Сохранить»

Предположим, это сохранение настроек объекта в многопользовательском приложении. Это условный пример, не предположение о твоём проекте.

| Поведение | Предпочтительное доказательство |
|---|---|
| Разрешённый пользователь сохраняет допустимые значения | Существующий или новый API/integration-сценарий |
| Недопустимые значения не меняют данные | Проверка контракта операции |
| Пользователь без права записи не может вызвать операцию напрямую | Authorization-сценарий |
| Пользователь не может изменить объект другого tenant | Проверка tenant boundary |
| Форма корректно отправляет данные и показывает результат | Браузерный сценарий |
| Повтор запроса не создаёт лишний эффект | Только если такой эффект существует и идемпотентность требуется контрактом |

Из этого **не следуют** отдельные тесты на каждый hook, setter, внутренний callback, CSS-класс и вызов функции.

Кроме того, если запрет записи и tenant isolation уже защищены подходящими тестами, не обязательно создавать их заново для каждой кнопки. Нужно подтвердить, что новая операция действительно проходит через проверяемую границу и не добавляет отдельный обход.

### 5.5. Проверять, что тест способен поймать дефект

Зелёный тест сам по себе — слабое доказательство.

Для bugfix желательно показать:

```text
До исправления → падение по ожидаемой причине.
После исправления → прохождение.
```

Для критического нового правила предлагаю выборочные проверки чувствительности: в одноразовой тестовой ветке временно убрать tenant filter, инвертировать разрешение или пропустить сохранение и убедиться, что нужный сценарий падает.

Это не требование достичь 100% mutation score. Это проверка, что ключевой тест действительно защищает заявленный риск.

Важно различать падение из-за бизнес-дефекта и падение из-за отсутствующей БД. Последнее не считается успешной демонстрацией red.

### 5.6. Разделить исследовательские проверки и постоянный suite

**Swarm может выполнить десятки временных проверок, но они не должны автоматически попасть в репозиторий.**

Постоянным regression-тестом становится минимальная проверка новой подтверждённой причины дефекта либо ранее незащищённого обязательного инварианта.

Именно здесь можно остановить вторую волну мусора: «агенты исследовали 80 вариантов, поэтому закоммитили 80 тестов».

### 5.7. Отдельный review тестов

Reviewer должен ответить по каждому добавленному сценарию:

> Какой отдельный дефект он ловит? Где независимый oracle? Нет ли уже такого сигнала? Переживёт ли тест внутренний рефакторинг? Почему выбран этот слой?

Необоснованный новый тест удаляется или объединяется с существующим. Но важный deny-case нельзя удалить исключительно ради красивого количества.

Полная процедура находится в пакете как `factory-test-design`.

## 6. RBAC swarm и verification skill poteto

**Здесь не «swarm или verification skill». Они решают разные задачи.**

Проектный verification skill объясняет, **как запустить приложение, управлять им и собрать доказательства**.

Swarm определяет, **кто и какие независимые проверки выполняет**.

У poteto `create-verification-skill` как раз требует исследовать репозиторий и создать реальные Launch, Doctor, Drive, Evidence и Cleanup. Причём сгенерированный skill должен быть исполнен хотя бы на одной реальной функции; непрогнанный документ остаётся черновиком. ([GitHub](https://raw.githubusercontent.com/cursor/plugins/main/pstack/skills/create-verification-skill/SKILL.md))

### Что проверять вместо простого «агент на роль»

Матрица должна иметь форму:

```text
actor × action × resource ownership × tenant × resource state
```

Например, два пользователя с ролью `manager` могут иметь разные права на конкретный объект.

Нужны проверки разрешённого пути, запрещённой операции, чужого объекта, другого tenant, прямого API-вызова, списков и экспорта. Скрытая кнопка не является доказательством серверного запрета. OWASP отдельно рекомендует проверки горизонтального доступа, повышения привилегий и tenant isolation через согласованную матрицу. ([cheatsheetseries.owasp.org](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Regression_Testing_Cheat_Sheet.html))

### Как я бы организовал выполнение

Каждый worker получает ограниченное задание:

```text
Версия приложения и SHA
Набор сценариев
Тестовые identities и объекты
Ожидаемая политика
Разрешённая среда и домены
Собственный worktree
Бюджет и условие остановки
Формат evidence
```

Не нужно выдавать задачу «сломай весь сайт любыми способами». Нужны обязательные сценарии и ограниченная исследовательская область.

Сначала выполняется детерминированная матрица. Затем adversarial-проход ищет обходы и сочетания, которые не покрыты базовыми проверками.

**Ожидаемая политика берётся из утверждённого контракта, а не генерируется из проверяемого authorization-кода.** Иначе ошибка реализации может стать одновременно ошибкой тестового expected.

### Изоляция важнее количества агентов

Отдельного worktree недостаточно. У параллельных проверяющих не должны случайно совпадать изменяемые данные, очередь задач, аккаунт или browser state.

Playwright отдельно указывает на необходимость независимого состояния и разных аккаунтов для параллельных тестов, меняющих серверные данные. ([playwright.dev](https://playwright.dev/docs/auth))

Поэтому предлагаю правило:

**Нет изоляции изменяемой среды — live-проверки выполняются последовательно.**

Все проверки проводятся в разрешённом preview с синтетическими данными. Production credentials, реальные платежи и реальные рассылки в этот контур не выдаются.

### Какие результаты принимать

У сценария четыре различных состояния:

```text
PASS / FAIL / BLOCKED / NOT_RUN
```

Отвалившийся браузер, отсутствующий fixture или пропавший worker не должны превращаться в «проблем не найдено».

Подход poteto `interrogate` здесь особенно уместен: finding принимается после воспроизведения, координатор повторяет проверку, одинаковые причины объединяются, а исправления не смешиваются с самим аудитом. ([GitHub](https://raw.githubusercontent.com/cursor/plugins/main/pstack/skills/interrogate/SKILL.md))

После исправления проверка повторяется на новом SHA. **Swarm дополняет regression suite, а не заменяет его и не доказывает полное отсутствие уязвимостей.**

## 7. Две реализации: Pi и OMP

Общий контракт фабрики должен оставаться одинаковым. Различаются адаптеры harness.

| Область | Pi | OMP |
|---|---|---|
| Управление сессией | SDK/RPC или управляемый процесс | SDK/RPC либо управляемый процесс |
| LSP и навигация | Подключаемые инструменты | Можно использовать встроенные LSP/AST-инструменты |
| Независимые workers | Собственный launcher | Для твоего требования worktree — тоже контролируемый launcher |
| Skills | Явно отобранный набор | Отобранный набор плюс контроль discovery и shadowing |
| Review | Адаптированная процедура | Нативный review можно использовать как correctness-проход |
| Память команд | Есть документированная интеграция TokenEconomizer | Совместимость TokenEconomizer требует отдельной проверки |
| Gate и evidence | Внешний controller | Тот же внешний controller |

Pi позиционируется как минимальный расширяемый harness; SDK/RPC доступны, а обязательной встроенной системы субагентов в ядре нет. OMP предоставляет больше штатных инструментов и специализированных агентов. Это различие состава, а не доказательство лучшего качества одного из вариантов. ([GitHub](https://raw.githubusercontent.com/earendil-works/pi/main/packages/coding-agent/README.md))

### Вариант Pi

Я бы использовал Pi как наиболее простой вариант для проверки самой модели управления:

```text
Pi extension
    → инструменты фабрики
    → controller
    → Worktrunk launcher
    → отдельные Pi workers
```

LSP, code intelligence и управление проверками подключаются отдельными адаптерами.

Hooks полезны для блокирования известных действий и показа стадии. Но extensions Pi выполняются с правами процесса. **Ограничение в hook не заменяет файловые права, sandbox и отсутствие опасных credentials.** ([GitHub](https://raw.githubusercontent.com/earendil-works/pi/main/packages/coding-agent/docs/extensions.md))

### Вариант OMP

Здесь я бы переиспользовал встроенные LSP, AST, browser и профильные определения агентов. Но не позволял им устанавливать альтернативные правила прохождения LAW.

Особенно важно для твоего случая: **по документации OMP субагенты по умолчанию работают в общем checkout**. Его режим изоляции может использовать clone/overlay, а успешные изменения штатно применяться к родительскому checkout. Это не эквивалент требованию «каждому отдельный Git worktree под Worktrunk». ([omp](https://omp.sh/docs/subagents))

Поэтому предлагаю внешний launcher:

```text
Controller создаёт worktree через Workspace Provider
                         ↓
Запускает отдельный OMP-процесс с cwd этого worktree
                         ↓
Получает результат и evidence
                         ↓
Сам решает, разрешена ли интеграция
```

Неконтролируемый native `task`, способный запустить editing-worker мимо этой процедуры, в таком профиле не должен быть доступен.

### Как устранить твой конфликт skills в OMP

У OMP одноимённые skills не объединяются. Один экземпляр перекрывает другой. В `/extensions` можно увидеть источник, активную и перекрытую версии; также есть фильтрация по именам. ([omp](https://omp.sh/docs/skills))

Для отдельного factory-профиля достаточно начинать с такого принципа:

```yaml
skills:
  enabled: true
  includeSkills:
    - "factory-*"
```

Это **фрагмент политики discovery**, не полная конфигурация и не установка skills.

Нужно проверить реальные зависимости и доступные tools. Простое переименование `tdd` без исправления внутренних ссылок может создать другую, менее заметную поломку.

### TokenEconomizer

В документированной интеграции Pi доступны micro-skills и loop guard; micro-skills по умолчанию выключены. OMP не указан как подтверждённый host, поэтому совместимость нельзя предполагать только из-за общего происхождения проектов. ([GitHub](https://raw.githubusercontent.com/microsoft/TokenEconomizer/main/plugin/README.md))

В твоей архитектуре память команд должна оставаться **советником**:

> Эта команда работала при таком cwd, lockfile, окружении и revision.

Она не должна становиться приказом исполнить команду из старой сессии. Тем более память не должна ослаблять обязательные проверки ради экономии токенов.

## 8. Tern и Worktrunk: один владелец worktrees

Здесь есть важная неоднозначность названия.

**Tern на `tern.build`** сам создаёт worktree на задачу и предоставляет очередь review. **Tern от Stencil** — другой продукт, workspace с интеграцией OMP. Поэтому я не закладываю непроверенное предположение, что любой Tern одинаково подключается к внешнему управлению worktrees. ([Tern](https://tern.build/))

Архитектурное правило для обоих вариантов одно:

> **Создание, привязка, интеграция и удаление worktree имеют одного владельца.**

Если владельцем выбран Worktrunk Provider, Tern должен работать с уже предоставленным workspace. Возможность такого подключения для конкретного Tern нужно подтвердить интеграционным прототипом.

Если Tern сам остаётся владельцем, Worktrunk нельзя одновременно заставить независимо управлять тем же lifecycle.

Worktrunk предоставляет управление worktrees и hooks, но я бы использовал hooks для подготовки среды и запуска проверок, а не как единственный механизм допуска или безопасности. ([Worktrunk](https://worktrunk.dev/))

**Постоянно работающий терминальный процесс также не равен надёжному workflow.** Контроллер должен уметь после сбоя выяснить, созданы ли уже ветка, preview или PR, и не повторять внешний эффект вслепую.

## 9. Что выполнять перед PR

Здесь я бы скорректировал твою последовательность.

**`improve-codebase-architecture` нельзя превращать в обязательный рефакторинг всего репозитория после каждой задачи.**

Текущий skill Matt предназначен для исследования архитектурных возможностей, показа предложений и обсуждения выбранного изменения. Это не автоматический завершающий шаг «улучши всё, что заметишь». ([GitHub](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/improve-codebase-architecture/SKILL.md))

Предлагаю два режима.

**На каждом существенном PR:** ограниченный архитектурный аудит изменённой области. Проверить дублирование, границы модулей, ненужные новые интерфейсы, соответствие ADR и влияние на тестируемость.

**Отдельной задачей:** полноценный `improve-codebase-architecture`, когда накопились конкретные точки трения.

Необязательная архитектурная возможность уходит в backlog. Исправление, необходимое для текущего контракта, возвращается исполнителю.

Последовательность завершения:

```text
Реализация
    ↓
Автоматические проверки
    ↓
Независимое review: spec + корректность + тесты + архитектурный diff
    ↓
Необходимые исправления
    ↓
Финальные проверки / runtime verification / требуемый RBAC audit
    ↓
Gate на итоговый SHA
    ↓
PR body
    ↓
Создание PR через разрешённый forge adapter
```

Любое изменение после проверки делает затронутые evidence устаревшими.

И ещё одна точность: **`pr` у Matt оформляет тело PR** — краткое изменение, evidence до/после и риск merge. Сам по себе этот skill не создаёт PR и не разрешает merge. ([GitHub](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/pr/SKILL.md))

## 10. В каком порядке это строить

Я бы сначала добился прохождения **одной реальной задачи от обсуждения до доказанного результата**, а не одновременно реализовывал всю инфраструктуру.

**Первый рабочий контур:** профиль проекта, системный аналитик, test contract, один ведущий агент, отдельный reviewer, Worktrunk, проверенный project verification skill и evidence на конкретный SHA.

**Второй контур:** RBAC-матрица, независимые fixtures, ограниченный adversarial-проход, восстановление после падений и проверка обходов gate.

**Третий контур:** semantic code search и session mining с измерением пользы относительно обычного поиска и LSP.

**Четвёртый контур:** несколько параллельных исполнителей, удалённые среды и распределённое выполнение.

Для Pi и OMP нужен один набор проверок самой фабрики: исполнитель пытается работать без допуска; reviewer пытается изменить продукт; результат относится к старому SHA; обязательный worker не вернулся; skill перекрыт другим; после падения повторно создаётся внешний эффект.

Метрики должны отвечать на практический вопрос: **стало ли меньше существенных переделок и вышедших дефектов при приемлемой стоимости принятого изменения?** Количество агентов, тестов и написанных строк здесь бесполезно.
